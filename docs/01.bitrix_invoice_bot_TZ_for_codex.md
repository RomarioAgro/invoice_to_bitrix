## 1. Назначение системы

Разработать Telegram-бота, который:

1. принимает от пользователя счёт в формате PDF или XLSX;
2. локально извлекает из файла реквизиты счёта;
3. позволяет проверить и исправить распознанные данные;
4. запрашивает недостающие сведения;
5. отправляет реквизиты и исходный файл в Битрикс;
6. сообщает пользователю результат отправки;
7. хранит незавершённый счёт ограниченное время и удаляет временные данные по установленным правилам.

Бот должен поддерживать одновременную независимую работу нескольких пользователей.

---

## 2. Термины

- **Счёт** — один загруженный пользователем файл PDF или XLSX и связанные с ним распознанные/введённые данные.
- **Подпись к файлу (`caption`)** — обычный текст, который пользователь отправляет в том же сообщении Telegram вместе с PDF или XLSX. В рамках данного ТЗ подпись является первичным источником описания счёта.
- **Активный счёт пользователя** — незавершённый счёт, который ещё не был успешно отправлен, отменён или удалён плановой очисткой.
- **Техническая обработка** — распознавание файла либо выполняющийся HTTP-запрос в Битрикс.
- **Ожидание пользователя** — состояние, в котором бот ожидает подтверждения, исправления поля или нажатия кнопки. Такое состояние не считается технической обработкой.
- **Попытка отправки** — HTTP-запрос в Битрикс, завершившийся неуспешным HTTP-статусом. Ошибка соединения и тайм-аут попытку не расходуют.
- **Успешный ответ Битрикс** — любой HTTP-ответ со статусом `2xx`.

## 3. Технологические требования

### 3.1. Основной стек

- язык разработки: Python 3.11 или новее;
- Telegram Bot API;
- режим получения обновлений: long polling;
- запуск: Docker-контейнер на VPS;
- конфигурация: `config.ini`;
- пример конфигурации без секретов: `config.example.ini`;
- секреты и исходная production-конфигурация Xray: локальный файл `D:\PythonProject\invoice_to_bitrix\.env`;
- подключение к Telegram Bot API: через локальный SOCKS5-прокси Xray на VPS;
- подключение к Битрикс: напрямую, без Xray и без иного proxy;
- распознавание PDF: локальный Tesseract OCR с языковым пакетом `rus`;
- преобразование страниц PDF в изображения: 300 DPI;
- чтение XLSX: Python-библиотека, работающая без Microsoft Excel;
- HTTP-взаимодействие с Битрикс: библиотека с поддержкой отдельного тайм-аута запроса;
- получение названия организации по ИНН: API DaData «Организация по ИНН или ОГРН»;
- подключение к DaData: напрямую, без Xray и без иного proxy;
- часовой пояс планировщика очистки: часовой пояс VPS.

Допускается выбрать конкретные поддерживаемые библиотеки внутри указанного стека. Выбранные библиотеки должны быть зафиксированы в файле зависимостей.

### 3.2. Ограничения

- платные AI API использовать нельзя;
- нельзя использовать сервисы, требующие обязательной привязки банковской карты;
- бесплатный AI API допускается только как необязательное дополнение;
- недоступность или исчерпание бесплатного AI API не должны останавливать локальную обработку;
- основная логика извлечения должна работать локально: текстовый слой PDF, XLSX, Tesseract OCR, шаблоны и регулярные выражения;
- Microsoft Excel, LibreOffice и графическая среда на VPS не должны требоваться;
- секреты нельзя размещать в исходном коде, Docker-образе, репозитории и `config.example.ini`.
- запрещено задавать глобальные переменные `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` или эквивалентные настройки процесса/контейнера: proxy настраивается только в экземпляре HTTP-клиента Telegram;
- HTTP-клиент Битрикс создаётся отдельно и не наследует proxy из окружения; использование proxy для запросов Битрикс запрещено.
- HTTP-клиент DaData создаётся отдельно, не наследует proxy из окружения и не использует SOCKS5-прокси Telegram;
- недоступность DaData не должна блокировать проверку, ручное заполнение или отправку счёта: в таком случае бот показывает ИНН без названия организации и записывает безопасную техническую ошибку в лог.

## 4. Поддерживаемые входные файлы

### 4.1. Форматы и ограничения

Бот принимает:

- `.pdf`;
- `.xlsx`.

Пользователь может добавить к файлу подпись в стандартном поле сообщения Telegram. Бот должен прочитать текст из свойства `caption` того же обновления, в котором получен файл, и использовать его как описание счёта. Отправлять описание отдельным сообщением одновременно с файлом не требуется.

Правила обработки подписи:

- используется текстовое значение `message.caption`, а не HTML- или Markdown-представление подписи;
- пробелы и переводы строк только в начале и конце удаляются;
- внутренний текст и переносы строк сохраняются;
- подпись, которая отсутствует, является пустой или после удаления краевых пробелов не содержит символов, считается неуказанным описанием;
- форматирование Telegram не переносится в Битрикс, сохраняется только обычный текст;
- подпись сохраняется только после того, как файл прошёл входную проверку и для него создано состояние активного счёта;
- подпись отклонённого файла не создаёт отдельный черновик и не изменяет текущий активный счёт пользователя.

Ограничения:

- максимальный размер одного файла — 5 МБ;
- PDF — не более 2 страниц;
- расширение и фактический тип файла должны проверяться;
- файл, не прошедший проверку, не создаёт активный счёт;
- неподдерживаемый или отклонённый файл удаляется из временного каталога.

### 4.2. Ошибки входного файла

Для неподдерживаемого формата бот сообщает:

> Поддерживаются только файлы PDF и XLSX.

Для файла больше 5 МБ:

> Размер файла превышает 5 МБ.

Для PDF больше 2 страниц:

> PDF должен содержать не более 2 страниц.

Для повреждённого или нечитаемого файла:

> Не удалось прочитать файл. Проверьте файл и отправьте его повторно.

Техническая причина записывается в лог, но пользователю не показывается traceback.

## 5. Правила приёма нового счёта

### 5.1. Один активный счёт на пользователя

У каждого пользователя может быть не более одного активного счёта.

Если пользователь отправляет новый файл при наличии активного счёта:

1. новый файл не принимается;
2. новый файл сразу удаляется;
3. текущий счёт и его состояние не изменяются;
4. бот предлагает завершить или отменить текущую обработку;
5. после завершения или `/cancel` пользователь должен отправить новый файл повторно.

Очередь файлов одного пользователя не создаётся.

### 5.2. Повторная загрузка

- хеш файла не вычисляется для блокировки повторов;
- повторная загрузка одного и того же файла разрешена;
- уникальный ID операции/idempotency key в Битрикс не передаётся;
- предварительная проверка дубликатов в Битрикс по номеру, дате и ИНН не выполняется.

### 5.3. Общий лимит технической обработки

Максимальное количество одновременно технически обрабатываемых счетов читается из:

```ini
[processing]
max_concurrent_invoices = 10
```

В лимит входят:

- распознавание PDF/XLSX;
- выполняющаяся отправка в Битрикс.

В лимит не входят счета, ожидающие:

- подтверждения пользователя;
- ввода или исправления данных;
- нажатия кнопки «Повторить».

Если при загрузке нового файла лимит занят:

1. файл не добавляется в очередь;
2. файл сразу удаляется;
3. активный счёт для пользователя не создаётся;
4. бот сообщает:

> Бот сейчас занят. Попробуйте отправить счёт позже

Автоматическая обработка после освобождения лимита не запускается. Пользователь должен отправить файл повторно.

## 6. Извлечение данных

### 6.1. PDF

Алгоритм:

1. попытаться извлечь встроенный текстовый слой;
2. преобразовать каждую страницу в изображение с разрешением 300 DPI;
3. выполнить Tesseract OCR с языком `rus`;
4. объединить доступный текстовый слой и результат OCR постранично с дедупликацией:
   - нормализовать пробелы, переносы строк, регистр и типографские символы для целей сравнения, не изменяя исходные значения извлекаемых полей;
   - удалить из результата OCR строки, которые после нормализации полностью совпадают со строками текстового слоя;
   - считать строку OCR дубликатом и не добавлять её повторно, если коэффициент сходства нормализованных строк не ниже `0,90` и все содержащиеся в них числовые последовательности совпадают; конкретный алгоритм расчёта сходства должен быть зафиксирован в коде и покрыт тестами;
   - если одна и та же подпись и значение найдены в обоих источниках, отдавать приоритет значению из встроенного текстового слоя;
   - сохранять уникальные строки OCR, которых нет в текстовом слое;
   - не удалять неоднозначные варианты реквизитов: при конфликте значений сохранить оба варианта для последующего выбора или исправления пользователем;
5. извлечь реквизиты по названиям полей, шаблонам и регулярным выражениям;
6. сохранить найденные варианты ИНН вместе с расположенными рядом названиями организаций.

Поддержка английского языкового пакета OCR не требуется.

### 6.2. XLSX

Алгоритм:

1. открыть книгу без выполнения макросов и внешних ссылок;
2. прочитать отображаемые значения ячеек доступных листов;
3. объединить текстовые значения в структуру, пригодную для поиска реквизитов;
4. извлечь реквизиты по подписям, шаблонам и регулярным выражениям;
5. не изменять исходный XLSX.

### 6.3. Общие правила распознавания

- поиск подписей выполняется без учёта регистра;
- лишние пробелы, неразрывные пробелы и переносы строк нормализуются;
- ИНН должен содержать 10 или 12 цифр;
- для поиска ИНН допускается шаблон вида `ИНН` + 10–12 цифр;
- денежная сумма нормализуется: убираются пробелы-разделители разрядов, запятая преобразуется в десятичный разделитель;
- даты распознаются как в числовом формате (`27.07.2026`, `27/07/2026`, `27-07-2026`), так и с русским названием месяца (`27 июля 2026`), и приводятся к формату `dd.mm.YYYY`;
- исходный текст документа не записывается целиком в лог;
- если поле не распознано, это не завершает обработку: пользователь должен иметь возможность ввести значение вручную.
- после распознавания каждого синтаксически корректного ИНН бот запрашивает в DaData название соответствующей организации по правилам пункта 7.2.1;
- название из DaData является информационным дополнением к ИНН, не заменяет ИНН и не передаётся в поля Битрикс вместо ИНН.

## 7. Данные, передаваемые в Битрикс

### 7.1. Карта полей

| Поле Битрикс | Тип | Источник и правило |
|---|---:|---|
| `TITLE` | string | Заголовок создаваемого элемента. Формируется из номера счёта; если номер ещё не указан, до отправки заголовок пересчитывается после ввода номера. |
| `UF_INVOICE_TYPE` | int | Код типа счёта. Пользователь выбирает один вариант из списка, заданного в `config.ini`. В текущей версии доступен вариант «Покупка оборудования, орг. техники и ПО» с кодом `329`. Архитектура и конфигурация должны позволять добавлять другие варианты без изменения логики диалога. |
| `UF_INVOICE_NUM` | string | Номер счёта. Извлекается из файла или вводится пользователем. Строка. |
| `UF_INVOICE_DATE` | string | Дата счёта в формате `dd.mm.YYYY`. |
| `UF_INVOICE_FROM_COMPANY` | string | ИНН заказчика/покупателя: 10 или 12 цифр. |
| `UF_INVOICE_TO_COMPANY` | string | ИНН исполнителя/поставщика: 10 или 12 цифр. |
| `UF_INVOICE_SUM_TO_PAY` | int | Сумма счёта к оплате в формате, требуемом существующим обработчиком Битрикс. Пользователь видит сумму в рублях; перед отправкой значение преобразуется к целочисленному формату поля. |
| `UF_INVOICE_PAY_BEFORE` | string | Срок оплаты в формате `dd.mm.YYYY`, если он указан в счёте или введён пользователем. |
| `UF_INVOICE_DESCRIPTION` | string | Описание счёта. Первичный источник — непустая подпись (`message.caption`) к сообщению с PDF/XLSX. Если подпись отсутствует или пуста после удаления краевых пробелов, бот запрашивает описание отдельным сообщением. Из содержимого PDF/XLSX описание автоматически не извлекается. Пользователь может изменить значение перед отправкой. |
| `UF_ARTICLES_DDS` | int | Идентификатор статьи ДДС. Пользователь выбирает одну статью из списка, заданного в `config.ini`. |
| `UF_SEARCH_TASK` | int | Обязательный номер задачи Битрикс. Положительное целое число. Проверка существования задачи через API не выполняется. |
| `UF_INVOICE_FILES` | array | Массив с исходным файлом: `DATA` — содержимое в Base64, `EXT` — фактическое расширение `pdf` или `xlsx` без точки. |
Выбор `UF_INVOICE_TYPE` и `UF_ARTICLES_DDS` в Telegram:

- бот отправляет сообщение с inline-клавиатурой;
- каждая кнопка содержит понятное пользователю название варианта;
- в callback-данных передаётся короткий внутренний идентификатор, а не полное название;
- после нажатия бот проверяет, что вариант существует в текущей конфигурации, и сохраняет соответствующий числовой код;
- сразу после успешного сохранения бот обязательно деактивирует клавиатуру в исходном сообщении выбора вызовом Telegram API `edit_message_reply_markup` с удалением inline-клавиатуры; деактивация выполняется до обновления или отправки сводки;
- затем бот обновляет сводку с учётом выбранного значения и автоматически возвращает пользователя к этапу проверки данных по пункту 8.3: если остались незаполненные обязательные поля — продолжает автоматический опрос по пункту 8.3.1, иначе показывает действия **«Продолжить»**, **«Изменить»** и **«Отменить»**;
- после сохранения значения callback исходной клавиатуры считается устаревшим; если Telegram не позволил удалить клавиатуру или пользователь повторно отправил тот же callback, бот не изменяет данные повторно и отвечает на callback уведомлением «Этот выбор уже обработан»;
- одновременно можно выбрать только один тип счёта и одну статью ДДС;
- при изменении поля текущий вариант отмечается текстом сообщения, а пользователю снова показывается список доступных вариантов;
- если число вариантов в будущем увеличится, кнопки выводятся вертикально или постранично так, чтобы размер callback-данных и клавиатуры оставался в пределах ограничений Telegram;
- названия и коды вариантов не должны быть захардкожены в обработчиках Telegram.

В текущей версии доступны статьи ДДС:

| Название | Код |
|---|---:|
| Оргтехника | `114830` |
| Программное обеспечение | `114845` |
| ТО кассовых аппаратов | `114789` |
| Ремонт и техобслуживание оргтехники | `114846` |

Формат файла:

```json
{
  "UF_INVOICE_FILES": [
    {
      "DATA": "<base64>",
      "EXT": "xlsx"
    }
  ]
}
```

Для PDF значение `EXT` должно быть `pdf`.

### 7.2. ИНН сторон

- в каждом счёте определяются ИНН заказчика и ИНН поставщика;
- `UF_INVOICE_FROM_COMPANY` — заказчик/покупатель;
- `UF_INVOICE_TO_COMPANY` — исполнитель/поставщик;
- один и тот же ИНН нельзя выбрать одновременно для обеих сторон;
- если стороны определены однозначно, значения подставляются автоматически;
- если найдено несколько ИНН и стороны определить нельзя, бот отдельно предлагает выбрать заказчика и поставщика;
- вариант выбора отображается как `Название организации — ИНН`;
- если название не распознано, отображается только ИНН;
- после выбора заказчика этот же ИНН исключается из доступных вариантов поставщика;
- пользователь должен иметь возможность ввести ИНН вручную.

### 7.2.1. Получение названия организации из DaData

Для каждого корректно распознанного, выбранного или введённого вручную ИНН бот выполняет поиск организации через API DaData:

```http
POST https://suggestions.dadata.ru/suggestions/api/4_1/rs/findById/party
Content-Type: application/json
Accept: application/json
Authorization: Token <DADATA_API_KEY>

{"query": "<ИНН>", "branch_type": "MAIN", "count": 1}
```

Требования:

- `DADATA_API_KEY` и `DADATA_SECRET_KEY` Codex получает из `D:\PythonProject\invoice_to_bitrix\.env`;
- для метода `findById/party` используется заголовок `Authorization: Token <DADATA_API_KEY>`; `DADATA_SECRET_KEY` нельзя без необходимости отправлять этому endpoint, поскольку данный метод его не требует;
- название берётся из первого подходящего результата в следующем порядке: `data.name.short_with_opf`, затем `value`, затем `data.name.full_with_opf`;
- результат принимается только в том случае, если `data.inn` в ответе точно совпадает с запрошенным ИНН;
- в сводке и вариантах выбора данные отображаются в формате `ИНН: 1234567890 — ООО «Название»`;
- если подходящий результат не найден, отображается только ИНН;
- если для одного ИНН API вернул несколько организаций/филиалов, при отсутствии КПП используется головная организация (`branch_type = MAIN`); неоднозначность не должна приводить к автоматической замене ИНН;
- запрос выполняется с отдельным настраиваемым тайм-аутом и прямым соединением без proxy;
- ответ кэшируется как минимум в пределах активного счёта, чтобы повторно не запрашивать один и тот же ИНН при каждом обновлении сводки;
- название организации является справочной информацией и не редактируется отдельным полем;
- отсутствие организации в DaData, HTTP-ошибка, тайм-аут или недоступность DaData не делают ИНН невалидным, не запрещают отправку и не расходуют попытки отправки в Битрикс;
- в логах разрешено записывать запрошенный ИНН, HTTP-статус и безопасное описание ошибки, но запрещено записывать ключи и полный ответ DaData.

### 7.3. Обязательная проверка перед отправкой

Перед отправкой бот проверяет:

- наличие обязательных значений: номера счёта, даты счёта, ИНН заказчика, ИНН поставщика, суммы, срока оплаты, описания, типа счёта, статьи ДДС и номера задачи;
- корректность дат;
- корректность ИНН;
- положительное целое значение номера задачи;
- положительное целое значение статьи ДДС;
- корректность суммы;
- различие ИНН заказчика и поставщика;
- наличие исходного файла;
- возможность прочитать и закодировать файл в Base64.

Проверка существования задачи, организаций и дубликатов через API Битрикс не выполняется.

Номер задачи является обязательным. Его отсутствие выделяется как ошибка, включает поле в автоматическую последовательность вопросов и блокирует подтверждение и отправку.

## 8. Пользовательский сценарий

### 8.1. Начало работы

Пользователь отправляет `/start`.

Если активного счёта нет, бот показывает:

- краткое назначение бота;
- поддерживаемые форматы PDF и XLSX;
- лимит 5 МБ;
- ограничение PDF до 2 страниц;
- предложение отправить файл.

Если активный счёт есть:

- процесс не сбрасывается;
- файл и введённые данные сохраняются;
- бот показывает статус и доступные действия так же, как `/status`.

### 8.2. Загрузка и распознавание

После успешной проверки файла бот:

1. создаёт изолированное состояние пользователя;
2. фиксирует дату и время загрузки;
3. читает `message.caption`, нормализует её по правилам пункта 4.1 и, если результат непустой, сразу сохраняет его в `UF_INVOICE_DESCRIPTION`;
4. сообщает о начале обработки;
5. извлекает остальные данные из файла; описание из содержимого PDF/XLSX не извлекается и не должно заменять значение, полученное из подписи;
6. получает в DaData названия организаций для найденных корректных ИНН;
7. показывает пользователю сводку полей;
8. если обязательные поля не заполнены, без дополнительного нажатия **«Продолжить»** начинает последовательный опрос по пункту 8.3.1.

Во время распознавания повторно запущенная обработка того же активного счёта не допускается.

### 8.3. Проверка данных

Сводка должна содержать понятные русские названия всех передаваемых полей и их текущие значения.

Правила отображения:

- заполненные и валидные поля отображаются обычным текстом;
- каждое незаполненное обязательное поле выводится отдельной жирной строкой с маркером `❗`, например: `❗ <b>Дата счёта: не указано</b>`;
- для форматирования используется HTML parse mode Telegram; все значения из документа, DaData и пользовательского ввода перед вставкой обязательно экранируются;
- произвольный красный цвет текста не используется, поскольку Telegram Bot API его не поддерживает; требование визуального выделения реализуется жирным текстом и маркером `❗`;
- незаполненный номер задачи показывается как обязательное поле: `❗ <b>Номер задачи Битрикс: не указано</b>`;
- рядом с каждым ИНН, для которого DaData вернула совпадающую организацию, показывается её название, например: `ИНН поставщика: 662345807403 — ООО «Пример»`;
- отсутствие названия организации не выделяется как ошибка, если сам ИНН заполнен и валиден;
- после каждого успешно введённого значения сводка обновляется, поэтому число выделенных строк последовательно уменьшается.

Доступные действия:

- **«Продолжить»** — перейти к итоговому подтверждению; кнопка доступна только тогда, когда все обязательные поля заполнены и валидны;
- **«Изменить»** — выбрать и изменить поле;
- **«Отменить»** — немедленно удалить счёт без дополнительного подтверждения.

Бот не должен заставлять пользователя загружать файл заново только из-за ошибки распознавания.

### 8.3.1. Автоматический последовательный опрос

Если после распознавания или изменения данных отсутствует хотя бы одно обязательное значение, бот сам, без нажатия **«Продолжить»**, запрашивает недостающие значения по одному.

Фиксированный порядок обхода:

1. номер счёта;
2. дата счёта;
3. ИНН заказчика;
4. ИНН поставщика;
5. сумма;
6. оплатить до;
7. описание;
8. тип счёта;
9. статья ДДС.
10. номер задачи Битрикс.

Правила диалога:

- уже заполненные и валидные поля автоматически пропускаются;
- если непустое описание было получено из подписи к файлу, пункт 7 автоматически пропускается и отдельный вопрос об описании бот не задаёт;
- если подпись отсутствует, пуста или содержит только пробельные символы, описание считается незаполненным; на пункте 7 бот отправляет отдельный вопрос: `Описание счёта не указано. Введите описание счёта.`;
- ответ на этот вопрос сохраняется в `UF_INVOICE_DESCRIPTION`; пустой ответ не принимается, бот повторяет вопрос об описании;
- для текстового поля бот отправляет отдельный понятный вопрос по шаблону: `Значение «Дата счёта» не указано. Укажите дату счёта в формате ДД.ММ.ГГГГ.`;
- формулировка вопроса и подсказка по формату адаптируются к конкретному полю;
- для ИНН сначала используются распознанные варианты с названиями организаций из DaData; если подходящего варианта нет, бот просит ввести ИНН вручную;
- после ручного ввода корректного ИНН бот запрашивает название в DaData, сохраняет результат и показывает его рядом с ИНН;
- для типа счёта и статьи ДДС вместо текстового ввода сразу показывается соответствующая inline-клавиатура;
- полученное значение валидируется до перехода дальше;
- при ошибке бот объясняет допустимый формат и повторяет вопрос только для текущего поля;
- после успешного ответа бот сохраняет значение, обновляет сводку и автоматически задаёт вопрос о следующем отсутствующем обязательном поле;
- номер задачи Битрикс запрашивается последним обязательным полем и принимается только как положительное целое число;
- после заполнения последнего обязательного поля бот показывает итоговую сводку с кнопками **«Продолжить»**, **«Изменить»** и **«Отменить»**;
- пользователь в любой момент может выбрать **«Изменить»** или выполнить `/cancel`; автоматический опрос не должен блокировать штатные команды;
- состояние должно явно хранить поле, ответ на которое ожидается сейчас, чтобы обычное сообщение пользователя не было записано в другое поле.

### 8.4. Изменение данных

После нажатия **«Изменить»** бот:

1. показывает список редактируемых полей;
2. предлагает выбрать одно поле;
3. просит прислать новое значение;
4. проверяет формат;
5. при ошибке объясняет допустимый формат и остаётся в режиме ввода этого поля;
6. при успехе сохраняет значение и заново показывает сводку.

Для номера задачи доступен ввод или замена положительного целого номера. Очистка обязательного поля и действие **«Не указывать»** не предоставляются.

Для неоднозначных ИНН используется выбор из найденных организаций либо ручной ввод.

Для полей, выбираемых inline-кнопками, в том числе `UF_INVOICE_TYPE` и `UF_ARTICLES_DDS`, новое текстовое значение от пользователя не запрашивается. После нажатия допустимого варианта бот выполняет действия строго в следующем порядке:

1. проверяет вариант по текущей конфигурации и сохраняет его код;
2. обязательно удаляет inline-клавиатуру из исходного сообщения выбора через `edit_message_reply_markup`;
3. обновляет существующее сообщение со сводкой либо, если его нельзя отредактировать, отправляет новую сводку;
4. показывает в сводке новое выбранное значение;
5. если остались незаполненные обязательные поля, автоматически задаёт вопрос о следующем поле по пункту 8.3.1; если обязательные поля заполнены, показывает кнопки **«Продолжить»**, **«Изменить»** и **«Отменить»**.

Таким образом, возврат к этапу проверки означает обязательный показ актуальной сводки и либо следующий автоматический вопрос, либо доступные действия **«Продолжить»**, **«Изменить»** и **«Отменить»**, когда обязательные поля уже заполнены.

Сразу после сохранения выбранного кода бот помечает callback исходной клавиатуры как обработанный. Если удалить клавиатуру из исходного сообщения не удалось, ошибка записывается в лог, но повторное нажатие на оставшуюся кнопку не должно повторно менять значение или нарушать состояние диалога. На устаревший callback бот отвечает уведомлением **«Этот выбор уже обработан»** и повторно показывает сводку только при необходимости.

После сохранения формы счёт получает новый набор из трёх попыток отправки. Фактическое изменение хотя бы одного значения для сброса попыток не требуется.

### 8.5. Подтверждение

Перед HTTP-запросом бот повторно показывает итоговую сводку.

Отправка разрешается только после прохождения локальной валидации. Отсутствующий или некорректный номер задачи считается ошибкой и препятствует отправке. Во время отправки состояние переводится в «отправляется в Битрикс». Бот редактирует существующее сообщение и удаляет из его inline-клавиатуры кнопку запуска отправки/повтора.

### 8.6. Успешная отправка

Любой HTTP-ответ Битрикс со статусом `2xx` считается успехом независимо от содержимого тела.

Бот:

1. записывает HTTP-ответ Битрикс в лог;
2. не ищет в теле ответа дополнительные признаки ошибки;
3. сообщает:

> Счёт успешно отправлен в Битрикс

4. если Битрикс вернул ссылку, добавляет её как кликабельную ссылку;
5. если ссылки нет, всё равно считает операцию успешной;
6. сразу удаляет исходный файл, распознанные данные и состояние диалога.

Если Битрикс создал счёт, но Telegram не смог доставить итоговое сообщение:

- ошибка доставки записывается в лог;
- операция остаётся успешной;
- повторная отправка в Битрикс не выполняется;
- автоматическая повторная доставка сообщения не требуется.

## 9. Ошибки Битрикс и повторные попытки

### 9.1. Общие правила

Максимум для одного сохранённого набора данных — 3 попытки, включая первоначальную отправку.

Попытку расходует только HTTP-ответ Битрикс с неуспешным статусом, то есть не `2xx`.

Не расходуют попытку:

- ошибка DNS;
- невозможность установить соединение;
- разрыв соединения до получения HTTP-ответа;
- тайм-аут;
- занятый общий лимит технической обработки;
- повторное нажатие кнопки во время уже выполняющейся отправки.

Автоматических повторных запросов нет.

### 9.2. Ошибка HTTP

При HTTP-статусе не `2xx` бот:

1. записывает статус и тело ответа в лог;
2. уменьшает число оставшихся попыток;
3. сохраняет исходный файл и введённые данные;
4. если попытки остались, показывает доступные действия:
   - **«Повторить»**;
   - **«Изменить»**;
   - **«Отменить»**;
5. после третьей ошибки больше не показывает **«Повторить»**;
6. после исчерпания попыток оставляет **«Изменить»** и **«Отменить»**.

После **«Изменить»** и сохранения формы пользователю снова доступны 3 попытки.

### 9.3. Ошибка соединения или тайм-аут

Бот:

- записывает техническую ошибку в лог;
- сохраняет счёт и данные;
- не уменьшает число попыток;
- позволяет нажать **«Повторить»** вручную;
- не выполняет автоматический повтор.

### 9.4. Занятый лимит при повторе

Если пользователь нажал **«Повторить»**, но общий лимит технической обработки занят:

- счёт и данные сохраняются;
- попытка не расходуется;
- запрос в Битрикс не создаётся;
- очередь не создаётся;
- бот сообщает:

> Бот сейчас занят. Попробуйте повторить позже

### 9.5. Защита от повторного нажатия

После первого нажатия **«Повторить»**:

- бот сначала атомарно устанавливает на стороне сервера состояние «отправляется в Битрикс»;
- затем бот редактирует сообщение с inline-клавиатурой и удаляет кнопку **«Повторить»**;
- на стороне сервера устанавливается блокировка отправки данного счёта;
- бот показывает:

> Счёт отправляется в Битрикс. Дождитесь результата

Если пользователь всё же отправит повторный callback, бот не запускает второй запрос, не расходует попытку и отвечает:

> Счёт уже обрабатывается. Дождитесь результата

Если Telegram не позволил отредактировать исходное сообщение, бот отправляет новое сообщение о текущем состоянии без кнопки **«Повторить»**. При этом старая кнопка может остаться видимой, но её callback считается устаревшим и блокируется серверной проверкой состояния.

Если запрос завершился ошибкой и попытки остались, кнопка **«Повторить»** появляется снова.

### 10.1. `/help`

Показывает:

- назначение бота;
- последовательность работы;
- поддерживаемые форматы;
- лимит 5 МБ;
- ограничение PDF до 2 страниц;
- команды `/start`, `/help`, `/status`, `/cancel`.

### 10.2. `/status`

Если активный счёт есть, показать:

- текущий этап;
- распознанный номер счёта;
- дату и время загрузки;
- оставшееся время до автоматического удаления;
- количество оставшихся попыток отправки.

- **«Продолжить»**;
- **«Изменить»**;
- **«Повторить»**;
- **«Отменить»**.

Недоступные действия не отображаются.

Если активного счёта нет:

> Нет счёта в обработке

### 10.3. `/cancel` и кнопка «Отменить»

При наличии активного счёта:

1. подтверждение не запрашивается;
2. обработка прекращается;
3. исходный файл и временные данные удаляются;
4. блокировки и состояние пользователя освобождаются;
5. бот сообщает:

> Обработка счёта отменена

Если активного счёта нет:

> Нет счёта в обработке

Кнопка **«Отменить»** действует точно так же, как `/cancel`.

---

## 11. Многопользовательская работа и состояние

- состояния пользователей изолированы по Telegram user ID;
- файлы разных пользователей хранятся в разных каталогах или под уникальными безопасными именами;
- пользователь не может получить доступ к чужому файлу, состоянию или результату;
- один пользователь не может параллельно отправить один счёт несколькими callback-запросами;
- общий счётчик технической обработки должен изменяться атомарно;
- освобождение лимита обязательно выполняется при успехе, ошибке, исключении и отмене;
- callback-кнопки проверяются на принадлежность активному пользователю и текущему состоянию;
- устаревший callback не должен запускать повторную операцию.

Состояние диалога хранится только во время работы процесса бота. После перезапуска контейнера оно не восстанавливается.

## 12. Хранение и очистка

### 12.1. Срок хранения

Незавершённый счёт, исходный файл и связанные временные данные хранятся 5 дней с момента загрузки.

- срок не продлевается после действий пользователя;
- через 5 дней данные подлежат удалению;
- уведомление пользователю не отправляется;
- результат очистки записывается в лог.
- срок хранения не продлевается при редактировании

### 12.2. Плановая очистка

Проверка выполняется один раз в сутки.

Время читается из:

```ini
[cleanup]
run_time = 03:00
retention_days = 5
```

`run_time` интерпретируется в часовом поясе VPS.

Очистка должна:

- удалить просроченные файлы;
- удалить связанные временные метаданные;
- удалить оставшиеся после перезапуска контейнера временные файлы, если истёк их срок хранения;
- не удалять данные моложе 5 дней только из-за перезапуска;
- безопасно пропускать файл, который в момент проверки технически обрабатывается;
- продолжать работу с остальными файлами при ошибке удаления одного объекта.

Оставшиеся после перезапуска файлы не удаляются немедленно при старте — только плановой очисткой.

## 13. Интеграция с Битрикс

### 13.1. Запрос

- URL обработчика Битрикс читается из переменной окружения `BITRIX_ENDPOINT_URL`, исходное значение которой Codex получает из файла `D:\PythonProject\invoice_to_bitrix\.env`;
- запрос выполняется методом POST;
- тело запроса содержит поля из раздела 7;
- исходный файл передаётся в `UF_INVOICE_FILES` в Base64;
- URL, токен или webhook Битрикс не должны быть захардкожены;
- тайм-аут запроса читается из конфигурации;
- HTTP-редиректы обрабатываются выбранной HTTP-библиотекой стандартно, итоговый статус используется для определения успеха.
- запрос выполняется прямым соединением без SOCKS5/HTTP proxy;
- клиент Битрикс должен игнорировать системные и унаследованные proxy-переменные окружения (`trust_env = false` либо эквивалент выбранной библиотеки);
- автоматические тесты должны подтверждать, что proxy, используемый Telegram-клиентом, не применяется к Битрикс.

### 13.4. Интеграция с DaData

- endpoint по умолчанию: `https://suggestions.dadata.ru/suggestions/api/4_1/rs/findById/party`;
- метод: POST;
- ключ API передаётся только в заголовке `Authorization: Token ...`;
- DaData вызывается отдельным HTTP-клиентом с `trust_env = false` либо эквивалентом;
- Telegram SOCKS5-прокси и глобальные proxy-переменные не применяются;
- тайм-аут читается из `[dadata] request_timeout_seconds`;
- для автоматических тестов endpoint должен подменяться через внедрение зависимости или настройку тестового окружения без изменения production-секретов;
- сбой DaData не меняет число попыток Битрикс и не блокирует отправку счёта.

### 13.2. Интерпретация результата

- любой итоговый HTTP-статус `2xx` — успех;
- тело успешного ответа записывается в лог;
- дополнительная проверка полей `success`, `result`, ID элемента и иных признаков не выполняется;
- наличие ссылки желательно использовать для ответа пользователю, но отсутствие ссылки не является ошибкой;
- любой итоговый HTTP-статус не `2xx` — ошибка API и расход одной попытки;
- ошибка соединения или тайм-аут не расходуют попытку.
- ответ Битрикс с ошибкой валидации (например, 400) трактуется как неуспешный HTTP-статус и расходует попытку

### 13.3. Тайм-аут

```ini
[bitrix]
request_timeout_seconds = 120
```

Значение должно быть положительным целым числом. При отсутствующем или некорректном значении бот не запускается и записывает понятную ошибку.

## 14. Конфигурация

### 14.1. Общие требования

- несекретные настройки приложения хранятся в рабочем файле `config.ini`;
- в репозиторий включается только `config.example.ini`;
- локальным источником production-секретов является `D:\PythonProject\invoice_to_bitrix\.env`;
- в этом `.env` должны находиться токен Telegram-бота, URL Битрикс, конфигурация Xray, `DADATA_API_KEY` и `DADATA_SECRET_KEY`;
- `.env`, его копии и производные production-файлы с секретами должны быть исключены через `.gitignore`;
- секретные значения передаются в контейнер через внешний файл конфигурации или Docker secret/переменные окружения;
- при запуске все обязательные параметры проверяются;
- при ошибке конфигурации бот завершает запуск с ненулевым кодом и понятной записью в лог;
- секреты не выводятся в лог.

[storage]

[logging]

retention_days = 30

[invoice_types]
purchase_equipment = 329|Покупка оборудования, орг. техники и ПО

[dds_articles]
office_equipment = 114830|Оргтехника

Токен Telegram, URL Битрикс и ключи DaData намеренно отсутствуют в `config.example.ini`: приложение получает их только из переменных окружения `TELEGRAM_BOT_TOKEN`, `BITRIX_ENDPOINT_URL`, `DADATA_API_KEY` и `DADATA_SECRET_KEY`.

### 14.3. Формат локального `.env`

Codex использует файл:

```text
D:\PythonProject\invoice_to_bitrix\.env
```

Если Codex запущен в WSL, тот же файл обычно доступен как `/mnt/d/PythonProject/invoice_to_bitrix/.env`. Исполнитель должен определить фактический доступный путь, не создавать второй источник истины и не выводить содержимое файла в терминал, отчёт или чат.

Обязательные имена переменных:

```dotenv
TELEGRAM_BOT_TOKEN=<секретный токен BotFather>
BITRIX_ENDPOINT_URL=<полный секретный URL обработчика Битрикс>
XRAY_CONFIG_JSON_B64=<конфигурация Xray в JSON, закодированная Base64 в одну строку>
DADATA_API_KEY=<секретный API-ключ DaData>
DADATA_SECRET_KEY=<секретный ключ DaData>
```

Допустимые необязательные параметры:

```dotenv
TELEGRAM_PROXY_URL=socks5://127.0.0.1:10808
TZ=Europe/Moscow
```

Требования:

- `XRAY_CONFIG_JSON_B64` после декодирования должен быть валидным JSON-конфигом Xray;
- если пользователь уже хранит конфигурацию Xray в `.env` под другим однозначно распознаваемым именем или в виде однострочного JSON, Codex может безопасно преобразовать её при развёртывании, но обязан документировать фактически поддержанное имя в `.env.example`;
- реальные значения не копируются в `.env.example`;
- на VPS из локального `.env` создаются только необходимые runtime-файлы: отдельный конфиг Xray и отдельный env-файл приложения;
- конфигурация Xray не передаётся в окружение контейнера бота;
- в окружение контейнера передаются только `TELEGRAM_BOT_TOKEN`, `BITRIX_ENDPOINT_URL`, `DADATA_API_KEY`, `DADATA_SECRET_KEY` и при необходимости `TELEGRAM_PROXY_URL`, `TZ`;
- локальный `.env` и runtime-файлы на VPS имеют права не шире `0600`;
- приложение при старте проверяет наличие токена, URL Битрикс и корректного URL локального SOCKS5-прокси, но не выводит их значения.

Формат значения в секциях `[invoice_types]` и `[dds_articles]`:

```text
<внутренний_идентификатор> = <числовой_код>|<отображаемое название>
```

Внутренний идентификатор должен быть уникальным в пределах секции и пригодным для безопасной передачи в callback-данных Telegram. При запуске бот проверяет уникальность идентификаторов и кодов, наличие названия и положительное целое значение кода. Некорректная конфигурация блокирует запуск с понятной записью в лог.

Значения, закреплённые требованиями:

- `request_timeout_seconds = 120`;
- тайм-аут DaData — 10 секунд;
- `max_concurrent_invoices = 10`;
- `max_send_attempts = 3`;
- `max_file_size_mb = 5`;
- `max_pdf_pages = 2`;
- `language = rus`;
- `dpi = 300`;
- `run_time = 03:00`;
- срок хранения счетов — 5 дней;
- срок хранения логов — 30 дней.

## 17. Docker и эксплуатация

### 17.1. Docker-образ

Dockerfile должен:

- использовать поддерживаемый компактный образ Python;
- установить Tesseract и русский языковой пакет;
- установить средства преобразования PDF, необходимые выбранной библиотеке;
- установить Python-зависимости из зафиксированного файла;
- запускать приложение не от root, если этому не препятствуют подключённые тома;
- не копировать `config.ini`, временные счета и логи в образ;
- содержать healthcheck или эквивалентную проверку работоспособности процесса.

### 17.2. Docker Compose

`docker-compose.yml` должен:

- запускать один экземпляр бота;
- использовать `restart: unless-stopped`;
- подключать `config.ini` только на чтение;
- подключать каталоги данных и логов;
- задавать часовой пояс, совпадающий с VPS;
- не публиковать входящий HTTP-порт, поскольку используется long polling;
- не содержать секретов.
- использовать `network_mode: host`, чтобы контейнер обращался к Xray по `127.0.0.1:10808`;
- загружать секреты приложения из отдельного runtime env-файла на VPS;
- не передавать контейнеру конфигурацию Xray и не задавать глобальные proxy-переменные.

Минимальный пример:

```yaml
services:
  bot:
    build: .
    restart: unless-stopped
    network_mode: host
    env_file:
      - ./.env.production
    volumes:
      - ./config.ini:/app/config.ini:ro
      - ./data:/app/data
      - ./logs:/app/logs
    healthcheck:
      test: ["CMD", "python", "-m", "app.healthcheck"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
```

Файл `.env.production` создаётся Codex на VPS из локального `D:\PythonProject\invoice_to_bitrix\.env`, не коммитится и имеет права `0600`. Он содержит только переменные, необходимые приложению: токен Telegram, URL Битрикс, ключи DaData, URL локального SOCKS5 и часовой пояс; `XRAY_CONFIG_JSON_B64` в него не включается.

Перед запуском на хосте создаются каталоги `./data` и `./logs`, а пользователь контейнера получает права на запись в них. Значение `TZ` задаётся равным часовому поясу VPS. Каталог `./data` сохраняет временные счета между перезапусками для последующей плановой очистки, а `./logs` сохраняет файловые логи и результаты их ротации.

`network_mode: host` используется только для доступа контейнера к loopback-порту Xray. Сам бот не слушает входящий порт, поэтому входящий сервис при этом не публикуется.

### 17.3. Перезапуск

После перезапуска контейнера:

- при старте бот не анализирует оставшиеся файлы, и они не считаются активными счетами;
- состояния диалогов и незавершённые операции не восстанавливаются;
- пользователь должен загрузить счёт заново;
- оставшиеся файлы не удаляются при запуске;
- оставшиеся файлы обрабатываются плановой ежедневной очисткой;
- очередь заданий не восстанавливается, поскольку очередь не предусмотрена.

## 18. Надёжность и безопасность

- имена загруженных файлов нельзя напрямую использовать как путь на диске;
- необходимо исключить path traversal;
- временное имя должно быть уникальным;
- расширение нужно нормализовать;
- размер проверяется до ресурсоёмкой обработки;
- PDF и XLSX открываются в безопасном режиме без выполнения вложенного кода;
- исходные файлы не должны быть доступны по публичному URL;
- callback-запросы Telegram должны проверяться на актуальность;
- операции изменения состояния одного пользователя должны быть защищены от гонок;
- счётчик общей обработки должен быть потокобезопасным/асинхронно безопасным;
- при неожиданном исключении счётчик и блокировка обязательно освобождаются;
- приложение должно корректно завершаться по `SIGTERM`;
- временный файл не должен удаляться до окончательного определения результата отправки;
- после HTTP `2xx` повторная отправка запрещена, даже если отправка сообщения в Telegram завершилась ошибкой.
- Telegram-клиент и клиент Битрикс должны иметь раздельные сетевые настройки;
- Telegram-клиент, клиент Битрикс и клиент DaData должны иметь раздельные сетевые настройки; DaData и Битрикс работают напрямую, а Telegram — через Xray;
- секреты Xray не должны быть доступны процессу бота;
- Xray должен слушать только loopback-интерфейс VPS и не должен создавать публично доступный proxy-порт.

- выделение незаполненного обязательного номера задачи;
- автоматический запуск последовательного опроса без нажатия **«Продолжить»**;
- пропуск вопроса об описании при наличии непустой подписи к файлу;
- запрос описания отдельным сообщением в установленной последовательности при отсутствующей, пустой или пробельной подписи;
- отклонение пустого ответа на отдельный вопрос об описании;
- пропуск уже заполненных полей, валидацию текущего ответа и переход к следующему незаполненному обязательному полю;
- включение номера задачи последним полем автоматического опроса;
- блокировку отправки без корректного положительного номера задачи;
- добавление `UF_SEARCH_TASK` с корректным положительным целым номером;
- запрос DaData по каждому уникальному корректному ИНН и повторное использование кэшированного результата;
- проверку точного совпадения запрошенного ИНН с `data.inn` в ответе DaData;
- выбор названия организации в порядке `short_with_opf` → `value` → `full_with_opf`;
- корректную работу при пустом ответе, HTTP-ошибке, тайм-ауте и некорректном ответе DaData;
- проверку конфигурации типов счетов и статей ДДС;
- формирование inline-клавиатур выбора типа счёта и статьи ДДС;
- возврат к обновлённой сводке после выбора типа счёта и статьи ДДС;
- обязательное удаление inline-клавиатуры из исходного сообщения до показа обновлённой сводки;
- отклонение повторного и устаревшего callback после сохранения выбранного значения;
- сериализацию полей Битрикс;

- расчёт срока хранения;
- расход и сброс попыток;
- классификацию `2xx`, не-`2xx`, тайм-аута и ошибки соединения;
- общий лимит обработки;
- защиту от повторного callback.

### 19.2. Интеграционные тесты

Использовать тестовые PDF/XLSX и имитацию Битрикс:

- `200` со ссылкой;
- `200` без ссылки;
- другой статус `2xx` с произвольным телом;
- `4xx`;
- `5xx`;
- тайм-аут;
- ошибка соединения;
- невозможность доставить итоговое Telegram-сообщение.
- сообщение с PDF/XLSX и непустой подписью заполняет `UF_INVOICE_DESCRIPTION`, а бот не задаёт повторный вопрос об описании;
- сообщение с PDF/XLSX без подписи, с пустой или пробельной подписью приводит к отдельному вопросу об описании в установленной последовательности;
- подпись к отклонённому файлу не создаёт черновик и не изменяет существующий активный счёт;
- Telegram Bot API доступен через тестовый SOCKS5-прокси;
- Битрикс вызывается напрямую и не использует SOCKS5-прокси Telegram;
- недоступность Xray нарушает Telegram-соединение, но не переключает Telegram на прямой обход proxy;
- наличие глобальной proxy-переменной в тестовом окружении не направляет запрос Битрикс через proxy.
- успешный ответ DaData добавляет название организации рядом с ИНН в сводке и вариантах выбора;
- DaData вызывается напрямую и не использует SOCKS5-прокси Telegram;
- недоступность DaData оставляет ИНН без названия, но не запрещает заполнение и отправку счёта;
- ключи DaData и полный ответ сервиса не попадают в логи.

### 19.3. Проверка конкурентности

Проверить:

- независимую работу нескольких пользователей;
- лимит 10 параллельных технических обработок;
- отсутствие очереди;
- отсутствие двойной отправки при повторном нажатии;
- освобождение лимита после исключения;
- сохранение счёта при занятом лимите во время «Повторить».

### 19.4. Проверка ротации логов

Проверить:

- создание нового ротированного файла при наступлении полуночи в часовом поясе VPS;
- сохранение постоянного имени активного файла;
- добавление даты в имя ротированного файла;
- удаление ротированных файлов сверх значения `[logging] retention_days`;
- сохранение записей в кодировке UTF-8.

### 19.5. Проверка Xray и маршрутизации

На VPS проверить:

- `xray.service` включена в автозапуск и находится в состоянии `active`;
- Xray слушает SOCKS5 только на `127.0.0.1:10808`;
- порт `10808` недоступен извне VPS;
- конфигурация проходит встроенную проверку Xray;
- запрос Telegram `getMe` через SOCKS5 завершается успешно;
- прямой `getMe` не используется ботом;
- запрос к согласованному безопасному URL Битрикс выполняется прямым соединением;
- после перезапуска VPS или контролируемого перезапуска служб Xray стартует автоматически раньше либо независимо от контейнера бота, а бот восстанавливает long polling после появления proxy;
- в логах systemd, Docker и приложения отсутствуют токен, URL Битрикс и содержимое конфигурации Xray.

## 20. Критерии приёмки

Работа считается выполненной, если одновременно выполняются все условия:

1. Бот запускается в Docker на VPS через long polling.
2. Команды `/start`, `/help`, `/status`, `/cancel` зарегистрированы в меню Telegram.
3. Бот принимает PDF и XLSX не более 5 МБ.
4. PDF больше 2 страниц отклоняется до OCR.
5. PDF распознаётся локально Tesseract `rus` при 300 DPI.
6. XLSX читается без установленного Excel.
7. Все поля из раздела 7 формируются и доступны для проверки/исправления; даты в числовом формате и с русским названием месяца нормализуются в `dd.mm.YYYY`; непустая подпись к PDF/XLSX записывается в `UF_INVOICE_DESCRIPTION`; номер задачи обязателен и передаётся положительным целым числом.
8. При объединении текстового слоя PDF и OCR дублирующиеся строки не размножаются, а конфликтующие значения не теряются.
9. Тип счёта и статья ДДС выбираются inline-кнопками из списков в конфигурации; после выбора бот сначала удаляет клавиатуру из исходного сообщения через `edit_message_reply_markup`, затем показывает актуальную сводку с действиями этапа проверки данных; повторный или устаревший callback не изменяет данные повторно; добавление нового варианта не требует изменения обработчиков Telegram.
10. Неоднозначные ИНН можно корректно назначить заказчику и поставщику; для каждого найденного ИНН бот пытается получить название организации из DaData и показывает его рядом с ИНН.
11. Один ИНН нельзя назначить обеим сторонам.
12. Каждое незаполненное обязательное поле, включая номер задачи, выделяется в сводке жирным текстом и маркером `❗`; бот без нажатия **«Продолжить»** последовательно запрашивает отсутствующие обязательные значения, валидирует каждый ответ и переходит к следующему полю.
12.1. При непустой подписи к сообщению с файлом бот использует её как описание счёта и не запрашивает описание повторно. При отсутствующей, пустой или пробельной подписи бот считает описание незаполненным и запрашивает его отдельным сообщением в установленной последовательности. Из содержимого PDF/XLSX описание автоматически не извлекается.
13. В Битрикс передаётся исходный файл в Base64 с правильным `EXT`.
14. Любой HTTP `2xx` считается успехом независимо от тела ответа.
15. При наличии ссылки она показывается пользователю; отсутствие ссылки не превращает успех в ошибку.
16. Неуспешный HTTP-статус расходует одну из трёх попыток.
17. Тайм-аут и ошибка соединения попытку не расходуют.
18. Автоматических повторов нет.
19. После третьей HTTP-ошибки кнопка «Повторить» скрывается.
20. После «Изменить» и сохранения формы предоставляются новые 3 попытки.
21. Повторное нажатие во время запроса не создаёт второй запрос.
22. Если общий лимит занят, очередь не создаётся.
23. При занятом лимите новый файл удаляется, а сохранённый счёт при «Повторить» не удаляется.
24. Один пользователь не может иметь два активных счёта.
25. Несколько пользователей работают независимо.
26. `/status` показывает этап, номер, время загрузки, срок хранения и оставшиеся попытки.
27. `/cancel` и «Отменить» удаляют данные сразу, без подтверждения.
28. После успеха временные данные удаляются сразу.
29. Незавершённые данные удаляются через 5 дней с момента загрузки плановой очисткой.
30. После перезапуска состояние не восстанавливается, а оставшиеся файлы не удаляются до плановой очистки.
31. Логи ротируются ежедневно в полночь по часовому поясу VPS встроенным `TimedRotatingFileHandler`; число сохраняемых ежедневных ротированных файлов определяется `[logging] retention_days = 30`.
32. В логах отсутствуют секреты, Base64 и полный текст исходного документа.
33. Некорректный обязательный параметр конфигурации блокирует запуск с понятной ошибкой.
34. В репозитории отсутствует рабочий `config.ini` с секретами; присутствует `config.example.ini`.
35. `docker-compose.yml` подключает постоянные каталоги данных и логов к `/app/data` и `/app/logs`.
36. Приложены автоматические тесты и README с командами сборки, запуска, остановки, просмотра логов и обновления.
37. На VPS установлен Xray как systemd-служба, включённая в автозапуск.
38. Xray предоставляет SOCKS5 только на `127.0.0.1:10808`; порт не доступен извне.
39. Все обращения бота к Telegram Bot API выполняются через Xray.
40. Все обращения к Битрикс выполняются напрямую, без Xray и без унаследованных proxy-настроек.
41. Секреты загружаются из `D:\PythonProject\invoice_to_bitrix\.env`, не попадают в Git, логи и итоговый отчёт; конфигурация Xray не передаётся контейнеру бота.
42. После контролируемого перезапуска служб Xray и бот автоматически возвращаются в рабочее состояние.
43. DaData вызывается отдельным прямым HTTP-клиентом без Telegram proxy; недоступность сервиса не блокирует отправку счёта.
44. `DADATA_API_KEY` и `DADATA_SECRET_KEY` загружаются из локального `.env`, передаются приложению через защищённый runtime-файл и отсутствуют в Git, логах и отчётах.
45. Поле `UF_SEARCH_TASK` всегда присутствует в JSON-запросе и содержит положительное целое число; отправка без него запрещена.

## 23. Исходные данные и доступы от пользователя

До начала production-развёртывания пользователь предоставляет Codex:

1. VPS уже задан SSH-алиасом `u24`;
2. настройки подключения, имя пользователя и ключ берутся из `~/.ssh/config`;
3. у настроенного SSH-пользователя есть доступ к необходимым командам через `sudo`;
4. токен Telegram-бота, URL Битрикс, конфигурация Xray, `DADATA_API_KEY` и `DADATA_SECRET_KEY` находятся в `D:\PythonProject\invoice_to_bitrix\.env`;
5. требуемый часовой пояс VPS и приложения — из `TZ` в `.env`, а при отсутствии значения используется фактический часовой пояс VPS;
6. Telegram-аккаунт для приёмочного теста;
7. по возможности — обезличенные примеры реальных PDF и XLSX;
8. при наличии — URL и доступ к Git-репозиторию.

Секреты не включаются в текст ТЗ, коммиты, отчёты, логи, примеры конфигурации и сообщения субагентам без необходимости. Предпочтительный порядок:

- SSH-доступ передаётся штатным защищённым способом среды, в которой запущен Codex;
- Codex читает секреты локально из `D:\PythonProject\invoice_to_bitrix\.env`, не просит пользователя повторно присылать их в чат и безопасно создаёт из них runtime-файлы на VPS;

- закрытые ключи пользователя не копируются в репозиторий и на VPS без отдельной необходимости;
- после размещения секретов Codex проверяет права доступа к файлам, но не выводит их содержимое.

Перед SSH-подключением Codex использует команду `ssh u24` и не подменяет параметры из `~/.ssh/config` ручными значениями без необходимости. Содержимое закрытого ключа и секретные параметры SSH в отчёт не включаются.

Если `ssh u24`, `sudo` либо чтение указанного `.env` недоступны, Codex должен выполнить все независимые локальные работы и тесты, после чего сообщить конкретный блокер. Повторно запрашивать токен, URL Битрикс или Xray-конфиг в чате не следует, пока существует доступный локальный `.env`.

## 24. Организация работы Codex

### 24.1. Планирование

Перед изменениями Codex:

1. изучает настоящее ТЗ целиком;
2. проверяет предоставленный каталог или репозиторий;
3. учитывает существующие файлы и незакоммиченные изменения, не удаляя чужую работу;
4. составляет короткий рабочий план с контрольными точками;
5. ведёт план до фактического завершения, а не до генерации кода.

### 24.2. Субагенты

Если Codex признаёт задачу сложной, рекомендуется параллельно делегировать субагентам независимые направления:

- Telegram-диалоги, состояния и защита callback;
- распознавание PDF/XLSX и извлечение реквизитов;
- интеграция DaData и обогащение ИНН названиями организаций;
- клиент Битрикс, сериализация и классификация ответов;
- тестирование конкурентности и негативных сценариев;
- Docker, безопасность и план развёртывания VPS.

Субагенты не должны одновременно редактировать один и тот же файл без координации. Главный агент:

- заранее распределяет границы модулей;
- проверяет каждый результат;
- самостоятельно читает итоговые изменения;
- запускает полный набор тестов после интеграции;
- не принимает отчёт субагента как замену фактической проверке.

### 24.3. Репозиторий и история

- Если репозитория нет, Codex создаёт Git-репозиторий.
- Если пользователь предоставил удалённый репозиторий, Codex работает в нём и отправляет изменения только в согласованную ветку.
- Секреты, `config.ini`, `.env`, логи, временные данные, OCR-артефакты и реальные счета обязательно исключаются из Git.
- Перед коммитом Codex проверяет индекс на отсутствие секретов и пользовательских документов.
- Коммиты должны быть логически разделены и иметь понятные сообщения.
- Перезапись опубликованной истории и force push без отдельного разрешения запрещены.

## 27. Требования к настройке VPS

### 27.1. Предварительная диагностика

Первое подключение к VPS начинается с безопасных read-only проверок:

- доступ командой `ssh u24` с настройками из `~/.ssh/config`;
- фактическое имя хоста;
- ОС, версия и архитектура;
- объём свободного диска и памяти;
- текущий часовой пояс и синхронизация времени;
- наличие Docker Engine и Docker Compose Plugin;
- состояние уже запущенных контейнеров;
- наличие ранее развёрнутой версии проекта;
- доступность DNS и исходящих HTTPS-соединений;
- права SSH-пользователя и доступность `sudo`;
- существующие правила firewall без их изменения.
- наличие Xray, его версия, расположение конфигурации, состояние службы и занятые loopback-порты;

Результаты, влияющие на развёртывание, Codex кратко фиксирует в рабочем отчёте. Секреты и лишние системные данные в отчёт не включаются.

### 27.2. Изменения на VPS

Codex самостоятельно:

1. устанавливает Docker Engine и Docker Compose Plugin, если они отсутствуют;
2. использует поддерживаемый для установленной ОС способ установки;
3. создаёт отдельный каталог приложения, по умолчанию `/opt/bitrix-invoice-bot`;
4. создаёт каталоги конфигурации, данных и логов с минимально необходимыми правами;
5. размещает исходный код или получает его из согласованного Git-репозитория;
6. создаёт production-конфигурацию на основе `config.example.ini`;
7. задаёт требуемый часовой пояс;
8. собирает образ на VPS либо использует заранее согласованный registry;
9. запускает ровно один экземпляр бота;
10. проверяет restart policy и healthcheck;
11. проверяет сохранение данных и логов при пересоздании контейнера.
12. устанавливает Xray и настраивает его как systemd-службу для доступа бота к Telegram согласно пункту 27.2.1.
13. проверяет прямой доступ к endpoint DaData без вывода ключей и без использования Telegram proxy.

Поскольку бот использует long polling:

- публичный порт приложения не открывается;
- reverse proxy, домен и TLS-сертификат для бота не требуются;
- Codex не должен без необходимости менять firewall.

### 27.2.1. Установка и настройка Xray

Codex обязан:

1. получить `XRAY_CONFIG_JSON_B64` из локального `D:\PythonProject\invoice_to_bitrix\.env` и декодировать его без вывода содержимого;
2. проверить, что получен валидный JSON;
3. установить актуальную стабильную версию Xray поддерживаемым для ОС способом без выполнения непроверенного shell-кода из сети через `curl | sh`;
4. разместить конфигурацию по стандартному пути установленного пакета, предпочтительно `/usr/local/etc/xray/config.json` либо `/etc/xray/config.json`;
5. установить владельца `root:root` и права `0600`;
6. сохранить пользовательскую outbound-конфигурацию и обеспечить SOCKS5 inbound:
   - protocol: `socks`;
   - listen: `127.0.0.1`;
   - port: `10808`;
   - UDP включать только при необходимости; для Telegram Bot API достаточно TCP;
7. не публиковать SOCKS5 на `0.0.0.0`, IPv6 wildcard или публичном интерфейсе;
8. до перезапуска проверить конфигурацию встроенной командой Xray;
9. при существующей конфигурации сначала создать защищённую резервную копию и не перезаписывать её без возможности отката;
10. включить и запустить службу командами, эквивалентными `systemctl enable --now xray`;
11. проверить `systemctl is-enabled xray`, `systemctl is-active xray` и фактическое прослушивание `127.0.0.1:10808`;
12. проверить доступ к Telegram Bot API через `socks5h://127.0.0.1:10808`, не выводя токен;
13. убедиться, что firewall не открывает `10808`; отдельное входящее правило для этого порта не создавать;
14. настроить приложение так, чтобы Telegram-клиент использовал `TELEGRAM_PROXY_URL`, по умолчанию `socks5://127.0.0.1:10808`;
15. настроить клиент Битрикс на прямое соединение и запретить ему наследование proxy из окружения;
16. не использовать прозрачную системную маршрутизацию, TUN, перенаправление всего трафика VPS или глобальные proxy-переменные.

Если проверка Xray не прошла, Codex возвращает прежнюю конфигурацию/службу в рабочее состояние, не запускает production long polling в заведомо неисправной конфигурации и сообщает конкретный блокер без секретов.

### 27.3. Ограничения безопасности на VPS

Без отдельного согласования запрещено:

- менять SSH-порт;
- отключать действующий способ входа;
- изменять пароли пользователей;
- запрещать root-доступ, если это может заблокировать пользователя;
- массово менять firewall;
- удалять сторонние контейнеры, каталоги или пакеты;
- обновлять всю ОС до новой версии;
- перезагружать VPS, если это не обязательно.

Если изменение потенциально может прервать SSH-доступ или работу чужого сервиса, Codex останавливается и запрашивает подтверждение.

### 27.4. Production-секреты

- Production-конфигурация не хранится в Git.
- Файл с секретами доступен только необходимому пользователю/группе.
- Способ монтирования конфигурации должен позволять приложению работать не от root.
- Токен Telegram и полный секретный URL Битрикс не выводятся командами диагностики, в логи и итоговый отчёт.
- Перед запуском Codex проверяет, что в образе и истории Git нет production-конфигурации.
- Исходный `.env` на компьютере пользователя не копируется на VPS целиком.
- На VPS создаются:
  - конфиг Xray с правами `0600`, доступный службе Xray;
  - `/opt/bitrix-invoice-bot/.env.production` с токеном, URL Битрикс, `DADATA_API_KEY`, `DADATA_SECRET_KEY` и URL локального SOCKS5, с правами `0600`.
- `XRAY_CONFIG_JSON_B64` не помещается в `.env.production` и не передаётся контейнеру.

### 27.5. Обновление и откат

Codex создаёт и документирует воспроизводимую процедуру:

1. резервное сохранение текущего Compose-файла и production-конфигурации без публикации секретов;
2. получение новой версии;
3. запуск тестов или минимальной проверки сборки;
4. сборка нового образа;
5. контролируемое пересоздание контейнера;
6. проверка healthcheck и логов;
7. возврат к предыдущему образу/коммиту при неуспешном запуске.

Процедура отдельно описывает безопасное обновление Xray: резервная копия бинарного файла/пакетной версии и конфигурации, проверка нового конфига до перезапуска, контролируемый restart, проверка SOCKS5 и возврат к предыдущей версии при ошибке.

Если на VPS уже существует версия бота, перед заменой Codex должен определить её каталог, Compose project name и способ запуска, сохранить возможность отката и не запускать параллельно второй long-polling экземпляр с тем же токеном.

## 28. Работа с регистрационными данными бота

После получения токена Codex:

1. читает его из локального `D:\PythonProject\invoice_to_bitrix\.env` и помещает только в защищённый `/opt/bitrix-invoice-bot/.env.production`;
2. запускает бота;
3. регистрирует команды `/start`, `/help`, `/status`, `/cancel` через Telegram Bot API;
4. проверяет `getMe` обязательно через локальный SOCKS5 Xray;
5. проверяет отсутствие webhook либо удаляет webhook штатным вызовом Telegram API через тот же SOCKS5 перед long polling;
6. убеждается, что не запущен другой long-polling процесс с этим токеном;
7. не публикует токен ни в одном результате.

Перевыпуск токена через BotFather остаётся действием пользователя. Если Telegram сообщает о недействительном токене, Codex показывает только безопасную формулировку ошибки и просит новый токен.

Прямой fallback к Telegram при недоступности Xray запрещён. Бот должен записать безопасную ошибку соединения и продолжить повторные попытки long polling с ограниченной задержкой средствами выбранной Telegram-библиотеки либо контролируемого цикла, не создавая интенсивный бесконечный цикл.
